# 실행·위임·검증

공통 기준은 [principles.md](principles.md), 모델 배정은 [models.md](models.md)에 둔다. 아래 수치 상한은 이번 하네스의 보수적 시작값이며 실험으로 조정한다. 런타임이 자동 강제하는 설정은 아니다.

## 경로 선택

현재 목표 → 최소 충분한 실행/검증 → 결과 판정 순서로 진행한다. 범위가 명확하면 메인이 직접 처리한다. 낯선 위치는 explorer, 의미 있는 설계 선택은 planner, 정해진 변경은 patcher, 구체적 결함 확인은 reviewer, 실행/실패 진단은 tester에 맡긴다. 다섯 단계를 모두 거치지 않는다.

고비용 연구는 질문·가설, 비교 대상, 데이터 중복/누수/분할, 지표·출력 실패 처리, 최종 평가 보호, 재현 조건과 자원 상한을 실행 전에 정한다. 중대한 설계·보안·연구 판단은 실행 전 reviewer를 배치한다. 어려운 판단은 DEEP 조건을 검토하되 모든 연구에 DEEP를 강제하지 않는다.

메인은 현재 계획을 단일 기준으로 결정한다. reviewer가 설계에 실질적으로 참여하면 그 부분의 독립 검토로 표시하지 않는다. 해결되지 않은 핵심 결함은 원본·테스트로 좁히고, 필수 검토가 불가능하면 공백을 보고한다.

## 전달 계약

```text
작업 ID / 역할 / 모드:
성공 기준 + 답할 질문:
필수 입력·현재 후보 ID·이미 확인한 근거:
산출물·검증 담당·반환 범위:
허용 읽기/쓰기 경로·명령·외부 제공자·자원·중단 조건:
요청 모델/추론 설정·실제 확인값 또는 미확인:
```

공통 원칙과 해당 역할만 붙인다. 전체 대화·파일 덤프 대신 관련 경로·구간·결정·실패 근거를 전달한다. 경로가 접근 불가능하면 허용된 발췌를 함께 준다. 핵심 맥락 누락을 토큰 절약으로 정당화하지 않는다. 전달 패킷은 별도 갱신 원장이 아니다.

기본은 메인 아래 한 단계 위임이며 재위임은 하지 않는다. 동시에 열어둘 전문 작업은 최대 2개로 시작한다. 독립 입력·파일·자원을 가질 때만 병렬화한다. patcher와 tester-repair는 같은 작업본을 동시에 수정하지 않는다. 비동기 실행은 런타임이 지원할 때만 사용하고, 없으면 순차/수동 전달로 표시한다.

## 결과와 부분 보완

반환은 `상태 → 산출물·변경 범위 → 실제 근거와 후보 ID → 미검증·다음 최소 행동`을 기본으로 한다. 역할별 추가 항목은 각 역할 문서에 있다. 전체 실행 로그는 허용된 위치에 두고 핵심 오류·명령·요약을 반환한다. 짧게 하느라 실패 조건을 빼지 않는다.

구현 결함은 patcher, 테스트/환경 문제는 tester, 접근법 문제는 planner, 근거 누락은 explorer의 해당 작업으로 돌린다. 동일 후보·조건에서 유효한 기존 검증은 재사용한다. reviewer가 본 후 제품/테스트/평가 설정을 고쳤다면 바뀐 부분을 다시 검증한다.

실패→수정→재검증 순환은 기본 2회까지 새 가설이 있는 보완으로 제한한다. 한 번의 검증에 필요한 테스트 개수를 제한하는 뜻은 아니다. 그 전에라도 같은 실패를 근거 없이 반복하면 멈춘다. 초과가 필요하면 원인·남은 범위·자원과 재계획을 보고한다. DEEP 상담은 동일 미해결 질문당 1회부터 시작한다. 자동 반복 리뷰·상시 감시자는 두지 않는다.

## 기록과 종료

현재 과업은 `task.md` 하나로 시작한다. 계획/근거/제출물이 커질 때 필요한 절만 별도 파일로 옮기고 링크를 남긴다. 기존 `brief/plan/state/evidence/result.md` 과업은 그대로 재개한다. 새 원장을 덧붙이지 않는다.

메인은 성공 기준별 판정과 실제 산출물·한계를 보고한다. 실패의 원인이 권한·환경·모델·과업 설계 중 무엇인지 구분한다. 재사용할 새 지식과 편집 권한이 있을 때만 지정 편집자가 [지식 운영](../playbooks/llm-wiki.md)으로 반영한다. 없으면 Wiki 조회/갱신 로그도 만들지 않는다.
