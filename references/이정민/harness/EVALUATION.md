# 하네스·모델 배정 실운영 비교 — 아직 미실행

역할 변경과 모델 교체의 효과를 따로 검증한다. 짧은 문서나 저렴한 토큰 단가만으로 효율 향상을 판정하지 않는다. 같은 원본 요구·코드 후보·데이터·도구·권한·성공 기준·Wiki 스냅샷을 사용한다.

## 비교 순서

A. v3 역할 체계와 v4 기능 체계를 같은 모델/추론 조건으로 비교한다.
B. v4 고정 상태에서 Sol 6.1 기본과 기존 Astra 기본을 비교한다.
C. v4 기본과 선택적 DEEP를 비교한다.
D. OpenAI가 없을 때 같은 역할 기준으로 Claude/Gemini 후보를 비교한다. 도구/API 차이는 별도 요인으로 기록한다.

동시에 모두 바꾼 비교는 전체 시스템 비교일 뿐 무엇이 효과를 냈는지 분리하지 않는다. 순서 영향을 줄이도록 독립 세션에서 순서를 섞고, 예산 내 반복한다. 앞 조건의 정답/패치를 뒤 조건에 넘기지 않는다. 프로필 명칭이 같은 추론량·비용을 뜻하지 않는다.

## 대표 과제

| 과제 | 기대 경로 | 필수 확인 |
| --- | --- | --- |
| 명확한 소규모 버그 | 직접 또는 patcher | 명세 충족·회귀 없음·불필요한 planner/DEEP 호출 없음 |
| 낯선 저장소의 제한된 변경 | explorer → 필요한 구현·검증 | 정확한 파일/의존 관계·범위 밖 변경 없음 |
| C/C++ 보안 모델 실험 설계 | planner + 필요한 사전 reviewer | 중복/정답 힌트·비교 조건·평가 실패·최종 평가 보호 |
| 테스트 실패 진단과 제한 수정 | tester verify → 허용된 repair | 원인·후보 구분·assertion/skip 조작 없음 |
| 지식 재사용 | 관련 Wiki 조회 → 실제 작업 | 현재 조건 확인·원자료 추적·무의미한 Wiki 갱신 없음 |

실제 프로젝트의 승인된 작은 과제를 선택한다. 목록은 예시이며 아직 정답 fixture를 배포한 것은 아니다. 테스트/실험 명령·라벨·평가셋을 미리 고정하고 출력 결과를 보고 유리하게 바꾸지 않는다.

## 새 모델의 역할 적합성

연결 확인 후 explorer는 숨겨둔 관련 파일/심볼을 정확히 찾는지, patcher는 명세된 경로만 바꾸고 회귀 테스트를 통과하는지, reviewer는 알려진 결함과 정상 변경을 구분하는지, tester는 환경 실패와 코드 결함을 구분하는지 확인한다. planner는 핵심 대안·검증 조건·연구 누수를 놓치지 않는지 평가한다.

읽기 전용/쓰기 범위/금지된 외부 전송은 비민감 임시 fixture에서 확인한다. 권한 위반은 품질 점수로 상쇄하지 않는다. 역할별 합격 기준은 실행 전에 정한다. “응답함”이나 모델의 자기평가만으로 합격시키지 않는다.

## 기록할 최소 값

| 값 | 기록 기준 |
| --- | --- |
| 성공/누락 | 필수 기준별 결과, 회귀/중요 결함, 검토 공백 |
| 사용량 | 역할·모델별 입력/캐시/출력/추론 토큰. 제공자 정의를 기록하고 포함된 추론 토큰을 이중 합산하지 않음 |
| 비용 | 실패·재시도·검토·도구 비용까지 실제 청구 기준. 미노출 구독 소모를 API 단가로 대신 계산하지 않음 |
| 시간 | 처음 요청부터 결과 검증까지, 실행/검토/대기 구분 |
| 협업 부담 | 호출·동일 자료 재조회·수정 횟수·사용자 개입·불필요한 문서 변경 |
| 재사용 | Wiki 최초 작성 비용과 후속 과업의 이익을 분리 |

전체 시도 비용/성공 건수는 실패 비용을 포함하되 성공 0건이면 정의되지 않음으로 표시한다. 성공률과 지연도 함께 보고하여 쉬운 과제만 통과한 저비용 구성을 선호하지 않는다. 소수 시험은 문제 탐지용이지 통계적 최적성의 증명이 아니다.

채택: 미리 정한 품질·안전 기준을 만족한 조건끼리 총비용·시간·개입을 비교한다. 열화가 있으면 해당 역할/검증만 보강한다. 이 문서 자체는 실험을 실행하거나 모델을 호출하지 않는다.
