# Escalation · Astra와 실패 처리

## Astra를 호출하는 조건

다음 중 하나이면 Sol은 SPECIALIST 또는 AUDITOR 작업을 만든다.

1. 인증/권한, sandbox 경계, 비신뢰 입력, 외부 실행, 데이터 보호처럼 보안상 중요한 동작을 설계·변경한다.
2. 여러 모듈에 큰 영향을 주거나 되돌리기 어려운 아키텍처 결정을 한다.
3. 동시성, parser, 프로토콜, 메모리/자원 고갈 문제를 현재 증거로 판단하기 어렵다.
4. 근거가 다른 두 설계가 남거나 검토자 사이에 중대한 의견 충돌이 있다.
5. 동일 원인에 대한 수정이 두 번 실패했거나 새로운 증거 없이 반복하고 있다.
6. Sol이 핵심 가정을 검증하지 못했거나 HIGH 변경의 최종 독립 감사가 필요하다.

보안 영향을 HIGH로 분류했다면 최초 설계 단계에서 가능할 때 검토하고, 최종 코드 후보도 확인한다.
설계 검토 통과는 이후 구현의 안전성 증명이 아니다.

## 역할별 승격

Luna가 수정 필요성을 발견하면 Sol에 보고한다. Sol이 Terra에 새 Builder 작업을 준다.
Terra가 계약/범위 변경이 필요하면 Sol에 보고한다. 스스로 쓰기 범위를 넓히지 않는다.
Sol이 고난도 판단을 좁힌 후 Astra에 전달한다. Astra는 최종 수용 권한을 가져가지 않는다.
Astra의 구현 아이디어는 제안이며, 실제 변경은 새 승인된 Builder 작업으로 처리한다.

## 원인을 구별한다

| 원인 | 다음 조치 |
|---|---|
| 필요한 코드·요구사항 누락 | 허용된 범위에서 추가 증거를 읽는다 |
| 권한/네트워크/라이선스/의존성 없음 | BLOCKED. 모델을 바꿔 제한을 우회하지 않는다 |
| 429/일시 장애 | 런타임 정책의 제한된 재시도 또는 작업 보류. 품질 하향 대체 금지 |
| 구현 가설 실패 | 반례와 명령 결과를 기록하고 가설 수정 |
| 두 번의 동일 원인 실패 | 자동 재시도 중단, Sol 재분류 후 필요 시 Astra |
| 독립 리뷰와 구현의 견해 충돌 | 주장별 근거·반례·재현 결과로 판단 |

두 번은 이 하네스의 초기 운영 기준이며 성능 연구에서 도출된 숫자가 아니다.

## Astra 부재

필수 Astra 게이트인데 접근 불가라면 `AUDIT_PENDING / BLOCKED`다.
테스트를 통과했다고 LOW/MEDIUM으로 내려서 승인하지 않는다.
권한 있는 사람이 사유·대체 검토자·한계를 기록하고 예외를 승인한 경우에만
동등한 전문 검토를 대체 절차로 수행한다. 이를 'Astra가 검토했다'고 기록하지 않는다.
모델을 바꿔 같은 역할을 수행한 경우 실제 모델과 변경 이유를 반드시 기록한다.

## 재작업 루프

실패 증거 → Sol 범위/가설 수정 → 새로운 Builder 작업 → 새 후보 → 재검증/재리뷰.
검토자가 직접 고치고 자신의 검토를 PASS로 바꾸지 않는다.
기존 결과를 재사용하려면 후보와 영향 범위가 동일함을 확인한다.

## 종료

BLOCKER/MAJOR가 해소되지 않으면 완료가 아니다.
필수 검증을 못 했으면 NOT_RUN/BLOCKED이며 PASS가 아니다.
예산이나 실행 시간이 소진되면 결과·남은 위험·다음 조치를 반환하고 자동 승인하지 않는다.
