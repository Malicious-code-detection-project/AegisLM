# Review / Verification / Acceptance

구현 완료, 검증 통과, 독립 리뷰 통과, 최종 수용을 분리한다.
최상위 기술 수용은 Sol이 책임진다. Git 병합·배포·운영 변경은 팀의 인간 승인/CI 규칙을 따른다.

## Verifier

Luna는 최종 후보와 `project.local.json` 또는 팀 문서에서 확인한 실제 명령을 사용한다.
먼저 명령·테스트 코드·설치 hook의 부작용을 검토한다. 비신뢰 저장소의 테스트도 실행 가능한 코드다.
필요한 최소 검증부터 실행하고 위험 또는 실패가 요구하면 범위를 넓힌다.
실행한 cwd, 명령, 종료 코드, 통과/실패 수, 로그 위치, 후보를 기록한다.
소스를 수정하거나 snapshot을 업데이트하거나 lint --fix로 결과를 통과시키지 않는다.

읽기 전용은 **프로젝트 소스에 대한 규칙**이다. 테스트가 캐시·빌드 파일을 만들 수 있으므로
승인된 격리 디렉터리를 사용하고 artifact scope를 기록한다. sandbox에서 막히면 BLOCKED로 보고한다.
공유 DB/네트워크/배포 환경을 사용하려면 팀 승인과 격리가 선행되어야 한다.

## 독립 Reviewer / Astra Auditor

새 컨텍스트에서 원 요구사항, 실제 diff, 관련 소스·call-site·테스트를 읽는다.
결함을 한 개 찾았다고 검토를 끝내지 않는다. 스타일 취향보다 동작·회귀·안전성에 집중한다.
Astra도 근거 없는 심각한 표현을 쓰지 않는다. 추정은 미확인 가설로 표시한다.

각 finding에는 ID, severity, 대상, 발생 조건, 영향, 근거, 필요한 수정/검증을 적는다.
유효한 반례가 있으면 작고 비파괴적인 테스트로 설명한다.
발견한 문제는 Sol에 반환하며 직접 패치하지 않는다.

## Severity

| 수준 | 의미 | 처리 |
|---|---|---|
| BLOCKER | 데이터 손실, 중대 보안 결함, 파괴적 오동작, 필수 빌드 실패 등 | 승인 금지 |
| MAJOR | 요구 동작 누락, 의미 있는 회귀, 잘못된 모듈 계약/상태 | 승인 전 수정·재검증 |
| MINOR | 핵심 동작을 무효화하지 않는 구체적 결함 | 수정 또는 Sol이 근거·담당자·추적 항목 기록 |
| QUESTION | 핵심 증거가 부족한 질문 | 해결 전 신뢰도/수용 기준 판단. 질문을 결함처럼 단정하지 않음 |

심각한 결함의 단순 '위험 수용'으로 기준을 우회하지 않는다. 요구사항을 바꾸려면 권한 있는 사람이
변경된 범위와 영향을 명시적으로 승인하고 새 기준으로 검토해야 한다.

## 위험별 gate

LOW: 의미 있는 검사 + Sol의 요구사항 확인. 실행 검사가 무의미한 문구 변경은 이유와 검토 근거를 남긴다.
MEDIUM: Verifier PASS + 독립 Reviewer PASS + Sol ACCEPT.
HIGH: 위험별 검증 PASS + 독립 리뷰 + Astra AUDITOR PASS + Sol ACCEPT.
HIGH에서 Astra가 전체 독립 리뷰를 겸하면 이를 명시한다. 좁은 보안 감사만 한 것은 기능 리뷰를 대신하지 않는다.
이상의 필수 단계가 NOT_RUN/BLOCKED면 최종 ACCEPTED 금지다.

## 후보 변경

검증·감사 후 소스 또는 관련 의존성/설정이 바뀌면 이전 PASS를 그대로 사용하지 않는다.
Sol은 영향 범위의 재검증과 재리뷰를 지정한다. 공유 환경의 데이터 변경도 검증 재현성에 포함한다.

## 최종 출력

무엇이 바뀌었는지, 실행 검증과 미실행 항목, review finding 처리, 남은 위험, 실제 사용 모델,
수용 상태를 [decision](../templates/decision.md)에 기록한다.
'비용을 무시해도 이 결과를 받아들일 수 있는가?'에 답할 수 있어야 한다.
