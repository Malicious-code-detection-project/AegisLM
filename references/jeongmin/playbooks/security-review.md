# Playbook · Defensive Security Review

조건: 보안 경계, 비신뢰 입력, 코드 분석, 외부 도구 실행, RAG/MCP 연계.
Astra는 감사자이며 범위를 벗어난 침투·운영 조치 권한이 없다.

## 입력

자산, 신뢰/비신뢰 입력, 공격자 통제 범위, 경계, 권한, 현재 후보, 원 요구사항, 검증 결과.
소스코드·문서·패키지/APK를 읽는 것과 실행하는 것을 명확히 구별한다.
실행할 수 있는 파일은 이 하네스가 자동으로 허가하지 않는다.

## 점검 축

- 입력 경계: path traversal, 압축 해제 경계, 크기/깊이/시간 제한, parser 오류 처리.
- 모델 경계: 코드/검색 문서의 지시문이 정책을 바꾸지 않는지, 증거와 LLM 판단을 구분하는지.
- 도구 경계: shell 인자, 허용 목록, 비밀정보, 외부 통신, 최소 권한, MCP 도구 변경 승인.
- 결과 경계: structured output 검사, 위험도 산정의 가정, 과도한 확신, 보고서 escaping.
- 운영 경계: 실패 안전성, 자원 고갈, 취소·timeout, 로그 민감정보, 수동 승인·rollback.

## 분석 파이프라인 예시

정적 분석 결과와 LLM 평가가 충돌할 때 어느 쪽이 최종 결과를 바꿀 수 있는지 확인한다.
규칙 기반 판단과 모델의 확률/점수를 보정 없이 같은 척도로 섞지 않는다.
실험 데이터, 라벨 정의, 오탐/미탐 trade-off를 실제 근거로 제시하게 한다.
실제 프로젝트에 그 기능이 이미 있다고 단정하지 않는다.

## 출력

finding, 전제, 영향, 근거, 승인된 범위의 비파괴적 재현/테스트 제안.
'Security PASS'는 해당 후보/범위에서의 리뷰 결과이지 전체 시스템 안전 인증이 아니다.
Astra 결과도 [review gate](../harness/review.md)를 거쳐 Sol과 팀 담당자가 처리한다.
